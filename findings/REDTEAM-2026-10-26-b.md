## 4. Split abort on maxFailedRecords / errorThreshold returns the failed item's message

**Verdict: FILE-MAJOR (borderline).** This is a code bug, not a doc issue and not intended.

**Summary:** camel-core - Splitter: when maxFailedRecords or errorThreshold aborts the split, the exchange carries the
failed split item's message and properties instead of the original input (unlike stopOnException).

**Reproduced** on main: `SplitterThresholdAbortKeepsOriginalMessageTest`, 8 tests. They fail for maxFailedRecords(1),
maxFailedRecords(2), errorThreshold(0.5), parallelProcessing+maxFailedRecords(1), and a doTry/doCatch around the
split. In the doCatch case, `mock:error` receives body "changed" (the item as the split steps modified it) where
"a,b,c" is expected. The controls pass: stopOnException keeps the original body, headers and properties; the
doCatch around a stopOnException split sees "a,b,c"; a split that stays under the threshold returns the original.
The test also shows the item's header and property leak into the original, and a property removed in the item is
restored.

**Root cause:**
- `core/camel-core-processor/src/main/java/org/apache/camel/processor/Splitter.java:574-614`:
  `shouldContinueOnFailure` returns false when the threshold is reached (598 `failureCount >= maxFailedRecords`, 606
  `ratio >= errorThreshold`).
- `MulticastProcessor.java:692-705` (async/parallel task) and `826-839` (sync task): the abort branch wraps the
  exception and calls `doDone(exchange, true)` with the sub-exchange.
- `MulticastProcessor.java:963-981` (`doDone`): `stoppedOnException = isStopOnException()` (965) is false for a
  threshold abort, because the threshold options exclude stopOnException. So instead of the stopOnException branch
  (973, which only propagates the exception) it runs `ExchangeHelper.copyResults(original, subExchange)` (978), which
  copies the item's message and properties into the original.
- On camel-4.22.x it is the same code, at MulticastProcessor 625/761 (the branches) and 900 (`doDone`).

**Docs and intent:**
- split-eip.adoc:380: "The Splitter will by default return the original input message."
- split-eip.adoc:1150-1152 and 1204: when the threshold is reached, the splitter "stops and sets an exception on the
  exchange". Nothing says the message is replaced.
- The CAMEL-23264 JIRA calls the options a generalization of `stopOnException()` "from boolean ... to ratio/count-based
  abort".
- In the CAMEL-23264 PR (#22300, discussion_r3513231533), the author (gnodet) wrote that users wanting zero tolerance
  "should use `stopOnException` or `maxFailedRecords(1)`", i.e. that the two are the same thing. The test shows they
  differ.
- Precedent: CAMEL-6802 (Claus, 2013), "Using stopOnException in splitter should not copy result back as we should
  preserve original exchange". It is the same rule for stopOnException; the new abort path skips it.

Nothing in the history shows a maintainer chose this. Not HOLD.

**Severity:** The exchange's message is silently replaced. When a doTry/doCatch, an onException in a calling route or
an outer dead letter channel (default useOriginalMessage=false) puts the failed input aside after the abort, it stores
the one modified item instead of the input. The items after the abort point are never processed, and they are not in
what was stored either, so they are lost. That is data loss in a documented combination, so Major.

It is borderline. With a route-level dead letter channel or a handled onException, the items' exceptions are already
handled inside the split, so the threshold never trips and the bug does not occur. And with the default error
handler, the caller does get an exception. If the doCatch case is judged a stretch, file it as Minor.

**Minimal fix:** Make the threshold abort take the same path as stopOnException in `doDone`. For example, the two
`!shouldContinueOnFailure` branches pass a "stopped on failure" flag (or `doDone` asks an overridable
`isStopOnFailure()`), and 965 becomes `stoppedOnException = isStopOnException() || stoppedOnFailure`. The original
then gets only the exception, as CAMEL-6802 does. errorThreshold uses the same branch, so it is fixed by the same
change.

**Duplicates checked:**
- JIRA text "maxFailedRecords"/"errorThreshold": 5 hits. CAMEL-23264 (the feature), CAMEL-24138 (tracker leak into
  nested splits), CAMEL-24143 (medium findings M1-M7: parallel ratio, non-failure stops recorded, successCount, watermark
  parse), CAMEL-24693 (YAML docs), CAMEL-23240 (closed). None is about the returned message.
- JIRA summary "stopOnException": CAMEL-6802 (the precedent above), CAMEL-24958, CAMEL-6627, CAMEL-3511, CAMEL-3362.
  None covers this.
- JIRA "splitter" + "original message" + "exception" since 2025-06: nothing relevant.
- `gh pr list --search maxFailedRecords` / "errorThreshold split": #22300, #24823 (CAMEL-24138), #26846 (CAMEL-24990,
  a review of the multicast family: streaming read-ahead, transacted context, recipient leak; it lists errorThreshold
  first-item abort as a follow-up, not this), #26351, #22159.
- PR #24883 (CAMEL-24143) changed shouldContinueOnFailure, not doDone.

**Affected versions:** 4.22.0, 4.22.1, 4.22.2, 4.23.0 and main (4.24.0-SNAPSHOT); camel-4.22.x has the same code.
Not 4.18.x or 4.14.x, where the options do not exist. CAMEL-23264's fix version is 4.22.0 (PR merged 2026-07-03).

## 5. A route without startupOrder gets a new auto number on every start, so a restart can clash

**Verdict: FILE-MINOR (backlog).** This is a code bug with a doc angle. Real, but transient and rare.

**Summary:** camel-core - A route without startupOrder is given a new auto-assigned startup order each time it is
started, so restarting it can fail with a spurious "Route startup order clash" FailedToStartRouteException.

**Reproduced** on main: `RouteRestartAutoStartupOrderClashTest`, 3 of 3 fail.
- (a) Route A (no startupOrder) and route B (startupOrder 1001). After stopRoute("A"), startRoute("A") throws
  "Route B already has startupOrder 1001".
- (b) Route A and route Z (startupOrder 10000, the docs' "should be safe" range). Restarts #1 to #8999 work; restart
  #9000 throws the clash with Z. The 9000 restarts take 0.22 s.
- (c) The context has autoStartup=false, with routes A (none), B (0) and C (1001). startAllRoutes() throws "Route A
  already has startupOrder 1001".

**Root cause:**
- `core/camel-base-engine/src/main/java/org/apache/camel/impl/engine/InternalRouteStartupManager.java:257-270`:
  `doPrepareRouteToBeStarted` gives `startupOrder = defaultRouteStartupOrder++` (264) on every prepare. That happens at
  context start (also for routes that do not start), on startRoute, startAllRoutes and resumeRoute, and on every
  supervising-controller retry.
- `doCheckStartupOrderClash` (273-300) then compares the new number with every entry of `getRouteStartupOrder()` and
  the current batch. A stopped route keeps its entry; only removeRoute drops it (AbstractCamelContext.java:1625).
- Context suspend also takes numbers: `AbstractCamelContext.java:2339`, `incrementRouteStartupOrder`.
- The list entry is deliberately not added twice on a restart (InternalRouteStartupManager 443-456, "we dont want to
  double add when restarting"), and the clash check skips the same route id "when using suspend/resume" (289-290). So
  restarts were considered for the list but not for the number.
- Two auto numbers can never clash, because the counter only grows. A clash needs an explicit number of 1000 or more.

**Docs:** configuring-route-startup-ordering-and-autostartup.adoc:188-191 reserves "numbers from 1000 upwards" for
Camel, so cases (a) and (c) use a number the docs tell users to avoid; those two alone would be NOT-A-BUG. But 193-196
says higher numbers may be used "to avoid collisions" and that "numbers starting from 10000 should be safe" (that
wording came from CAMEL-12988, 2018), and case (b) shows it is not safe after enough restarts.

**How common:** Routes without startupOrder are the norm. Restarts happen through JMX/Hawtio, `camel cmd`, route
policies, and the supervising route controller. The controller's default backOffMaxAttempts=0 means unlimited retries,
every 2 s by default (DefaultSupervisingRouteController:253), and each retry takes a number, so about 5 h of failed
retries reaches 10000. Dev-mode route reload removes the route (its entry goes) and adds it back with a fresh number,
so it can only clash with an explicit number of 1000 or more.

**Severity:** The failure is transient: the next attempt gets the next number and succeeds. Its message is misleading
("Please correct startupOrder"), and it only happens with explicit numbers of 1000 or more. No hang, data loss or dead
consumer, so Minor. If the maintainers prefer, the alternative is a DOC note that auto numbers keep increasing, with
a recommendation of numbers well above 10000.

**Minimal fix:** In `doPrepareRouteToBeStarted`, reuse the startup order of the route's existing `RouteStartupOrder`
entry (or a routeId-to-number map in InternalRouteStartupManager, cleared in doRemove), and only call
`defaultRouteStartupOrder++` the first time. Context suspend (2339) should reuse it too.

**Duplicates checked:**
- JIRA: "startup order clash" / "startupOrder clash" / summary "startupOrder": only CAMEL-12988 (the doc update for
  10000).
- JIRA "defaultRouteStartupOrder" / "InternalRouteStartupManager": CAMEL-24404 (exception wrapping), unrelated. The
  rest of the 51 hits are noise.
- JIRA "auto assigned" or "startupOrder" since 2019: nothing relevant.
- gh "startupOrder", "startup order clash", "defaultRouteStartupOrder": #27632 (CAMEL-25500, stop-all drain;
  AbstractCamelContext and test only) and the CAMEL-25000/25157/24831/25823/25062 PRs. None touches the numbering.

**Affected versions:** All of them. The same code (`defaultRouteStartupOrder++`) is at InternalRouteStartupManager:264
on main and 4.22.x and at 269 on 4.18.x and 4.14.x. It is long-standing; the shallow clone hides its origin.

## 6. stopRoute, then suspendRoute, then resumeRoute: the route reports Started but its consumer is stopped

**Verdict: FILE-MINOR.** A code bug, the general form of the 2014 CAMEL-7855, which was fixed only in camel-jms.

**Summary:** camel-core - suspendRoute of a stopped route marks it Suspended, and resumeRoute then reports it Started
without starting its consumer.

**Reproduced** on main: `RouteSuspendOfStoppedRouteTest`, 2 of 2 fail.
- seda route: after stopRoute, suspendRoute and resumeRoute, the route status is Started but `consumer.getStatus()` is
  Stopped.
- direct route: after the same calls the status is Started, and sending to `direct:d?block=false` throws
  DirectConsumerNotAvailableException.
- The route logger even logs "Route: S resumed and consuming from: seda://s".

**Root cause:**
- `AbstractCamelContext.java:1655-1685` (`suspendRoute`) does not check the route status. It calls the shutdown
  strategy and then `suspendRouteService` (3852-3861), which calls `routeService.suspend()`.
- `core/camel-api/src/main/java/org/apache/camel/support/service/BaseService.java:194-218` (`suspend`) only skips
  SUSPENDED and SUSPENDING, so a STOPPED service becomes SUSPENDED. This is the gap the CAMEL-7855 reporter pointed at
  in 2014.
- `resumeRoute` (AbstractCamelContext.java:1390-1415) goes to `resumeRouteService` (3768-3787). The route service is
  "suspended", so it takes the resume path (3773).
- InternalRouteStartupManager.java:411-413 calls `ServiceHelper.resumeService(consumer)`, which does nothing on a
  stopped consumer (BaseService.resume:229 only resumes SUSPENDED).
- Then `routeService.resume()` (AbstractCamelContext.java:3781) sets the route service to STARTED.

**Docs and allowed-ness:**
- ServiceStatus.isSuspendable() (ServiceStatus.java:57) is true only for Started.
- RouteController.resumeRoute javadoc (229) says it "Resumes the given route if it has been previously suspended".
- No doc says that suspend of a stopped route is allowed or refused; ManagedSuspendableRoute.suspend only checks that
  the context is started.
- History: in CAMEL-7855 (same symptom: a stopped JMS route, then suspend and resume, "reports itself as being in
  state Started", not consuming), Claus answered "you should start it first" but fixed camel-jms (066331947f46) for a
  route that was never started. The reporter's proposals were to throw or to make suspend of a stopped route a no-op.
  The core was never changed, and the stop-then-suspend variant still fails for every component.
- No maintainer chose "Started but not consuming"; Claus called the call sequence a user error and still fixed it. So
  not HOLD, but expect the "start it first" answer, and lead with the CLI path below.

**How it happens in normal use:** `camel cmd suspend-route *` / `resume-route *` (LocalCliConnector.java:1387-1407)
loop over all routes, including routes stopped on purpose. Afterwards such a route shows Started (CLI, JMX, health
checks) while consuming nothing. A later startRoute repairs it, because InternalRouteStartupManager.isStartable looks
at the consumer's own status.

**Severity:** The status is wrong, but the route that "silently consumes nothing" was one the operator had stopped,
so no input is lost. No hang or wrong routing, so Minor.

**Minimal fix:** In `AbstractCamelContext.suspendRoute`, do nothing (log at debug) when the route is not Started, i.e.
`!routeService.getStatus().isSuspendable()`. This is the reporter's option 2 in CAMEL-7855. Alternatively,
`resumeRouteService` could start the route when its consumer is not suspended.

**Duplicates checked:**
- JIRA: summary "suspendRoute"/"resumeRoute"/"suspend"+"stopped"; text "suspend a stopped"; "stopped route"+"suspend"
  since 2020; "reports Started". The hits are CAMEL-7855 (related, above) and the 2026 component-level suspend fixes:
  CAMEL-25848, 25503, 25314, 25312, 25297, 25018, 24951, 25872, 25315. None is about suspendRoute of a stopped route
  in core.
- gh "suspendRoute stopped", "suspend stopped route", "resumeRoute": the PRs for those JIRAs (#28321, #27636, #26883,
  #27388, #27338, #26867, #26797, ...). None changes AbstractCamelContext.suspendRoute or BaseService.suspend.

**Affected versions:** All of them. The same code is on main, 4.22.x (suspendRoute at 1595, resumeRouteService check
at 3711), 4.18.x (1538/3635) and 4.14.x (1460/3554), and BaseService.suspend has no status guard on any of them.
