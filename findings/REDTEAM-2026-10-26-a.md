## 1. Routing slip: redelivery of a step hangs after a routing slip in the called route ran on the same exchange

**Verdict: FILE-MAJOR**

**JIRA summary:** camel-core - Routing Slip / Dynamic Router: redelivering a step hangs for ever (NPE in
RoutingSlipProcessor, swallowed) when the called route used a routing slip itself

**Root cause (lines at origin/main 426c3f8a4cb8):**
- `RoutingSlip.java:424`. `processExchange` stores the step's producer in the exchange property `SLIP_PRODUCER`. The
  error handler that wraps each slip step does not call the producer directly. It calls `RoutingSlipProcessor`
  (`RoutingSlip.java:582-583`), which reads the producer back from that property on every attempt.
- `RoutingSlip.java:429`. When a step completes, `done()` *removes* `SLIP_PRODUCER`. It does not restore the previous
  value. The exchange is shared: direct passes the same Exchange object to the called route. So a routing slip (or
  dynamic router) in the called route overwrites the outer step's property and then removes it.
- The exception then escapes the called route back to the outer step's error handler, which redelivers:
  `RedeliveryErrorHandler.java:1360` (`RedeliveryTask.redeliver`) -> `RoutingSlipProcessor.process`, where
  `RoutingSlip.java:583` throws `NullPointerException: "producer" is null`.
- The redelivery runs as a reactive task. `DefaultReactiveExecutor.java:205-207` (`Worker.doRun`) catches the NPE,
  logs a WARN ("This exception is ignored") and never calls the AsyncCallback. The caller parks in
  `DefaultAsyncProcessorAwaitManager.await` (`:105`) for ever, and the exchange stays in flight.

The trace was confirmed by instrumenting RoutingSlip (SET/REMOVE/redeliver log; output in this session, summarised):
```
SET    slip=outer ex=E ep=direct://r1  (error handler wraps the step)
REDELIVER-TO-SLIP-PRODUCER ex=E producer=Producer[direct://r1]     <- first attempt
SET    slip=inner ex=E ep=mock://m1   (route r2)
REMOVE slip=inner ex=E ep=mock://m1
REDELIVER-TO-SLIP-PRODUCER ex=E producer=null slipEndpoint=mock://m1   <- redelivery -> NPE -> lost callback
```
The test log (`logs-rtcs-a/main-repro-camel-core-test.log:102-107`) has the NPE stack at origin/main.

**Much smaller than the campaign route.** You do not need nested doTry, `handled`, `onException`, two slip steps or a
`mock` first step. You need three things: a routing slip step with redelivery, a called route that runs a routing slip
or dynamic router, and an exception that leaves that called route unhandled. The exception can leave through a
top-level doTry without a matching doCatch, through `noErrorHandler()`, or through a rethrow.
(`logs-rtcs-a/probes/Min.java`, the same results on main, 4.22.1 and 4.23.0):

| variant | result |
|---|---|
| `defaultErrorHandler().maximumRedeliveries(1)`; `from(a).routingSlip("direct:b")`; b = `doTry().routingSlip("mock:x").throwException(ISE).endDoTry().doFinally().end()` | HANG |
| `deadLetterChannel("mock:dead").maximumRedeliveries(2)`; b = `errorHandler(noErrorHandler()).routingSlip("mock:x").throwException(ISE)` | HANG |
| onException handled / not handled, maximumRedeliveries 1 | HANG / HANG |
| inner `dynamicRouter` instead of the inner routing slip | HANG |
| inner `recipientList` instead of the inner routing slip (does not use SLIP_PRODUCER) | returns |
| no redelivery (maximumRedeliveries 0) | returns |
| no inner slip (control) | returns, ISE |

The finding's table says the not-handled and single-`direct:r1` variants return. That holds for its larger route, but
not for the minimal shape: the only requirements are redelivery and the shared-exchange inner slip.

**Docs:** no documentation allows a hang. error-handler.adoc 29-31 says the exception is propagated back to the
caller. The DLC and redelivery docs say the message is redelivered and then sent to the DLC. With the DLC variant,
`mock:dead` never gets the message.

**Reproducer:** `logs-rtcs-a/tests/RoutingSlipNestedRoutingSlipRedeliveryTest.java` (package
`org.apache.camel.processor`, ContextTestSupport, `assertTimeoutPreemptively(10 s)`, no sleeps). All 3 tests time out
on origin/main ("execution timed out after 10000 ms"; `logs-rtcs-a/main-repro.log`). The third test is the campaign
route (HangRepro). Original probe: `harness/probes/HangRepro.java`.

**Minimal fix (validated in a scratch overlay on aa63c0a, not in the repo; sketch in `logs-rtcs-a/f1-fix-sketch.diff`):**
in `processExchange`, remember the previous `SLIP_PRODUCER` before line 424 and restore it in `done()` at line 429
instead of removing it unconditionally. With that change, all 9 Min variants and HangRepro return, and the variants
that are not handled return the ISE. Optional hardening: `RoutingSlipProcessor.process` should fail the exchange
(`setException` + `callback.done(true)`) when the property is missing, so that a regression cannot turn into a hang.

**History:** the SLIP_PRODUCER design comes from CAMEL-8393 / CAMEL-10050 (per-step error handler for routing slip and
dynamic router, 2.16-2.18). CAMEL-24993 (4.23.0 deep review of toD/Routing Slip, merged as 0e0be00e8bfb) touched the
same `done()` (prototype stop) but not the remove. No maintainer decision covers this. The local clone is shallow
(boundary 025f7cb97232, 2026-09-15), so older blame was not available locally.

**Duplicates checked (none):** JIRA REST text searches: `routingSlip` x (hang | redelivery | NullPointerException |
SLIP_PRODUCER); `SLIP_PRODUCER` / `RoutingSlipProcessor`; summary (routing slip | dynamic router) x (nested | hang |
NPE | redeliver* | error handler). Hits checked: CAMEL-8393, CAMEL-10048/10050, CAMEL-7705 (cannot reproduce, bean
binding), CAMEL-7736, CAMEL-24993; none is this bug. `gh pr list -R apache/camel --state all --search`: "SLIP_PRODUCER",
"routing slip redelivery", "RoutingSlipProcessor", "routingSlip nested hang" gave no hits.

**Affected versions:** main (4.24.0-SNAPSHOT), 4.23.0 and 4.22.1 were reproduced. On camel-4.22.x, camel-4.18.x and
camel-4.14.x the code is identical: set/remove at 424/429 (4.22.x) and 404/409 (4.18.x, 4.14.x), the NPE line at
582/560/560, and the same `DefaultReactiveExecutor` swallow. Every supported line is affected.

## 2. Failover load balancer fails over on a suppressed exception and swallows the real, unmonitored failure

**Verdict: FILE-MINOR** (a 4.23.0 regression from CAMEL-25114, combined with older matching of suppressed exceptions)

**JIRA summary:** camel-core - Failover load balancer: fails over on an exception that is only suppressed (e.g. thrown
in a doFinally) and drops the unmonitored exception that failed the attempt

**Root cause:**
- `FailOverLoadBalancer.java:133-139` (`shouldFailOver`) decides with `exchange.getException(exception)` for each
  monitored class.
- `ObjectHelper.java:1269-1274` (`getException(Class, Throwable)`) checks `getSuppressed()` *before* the cause chain.
  This was a deliberate change for CAMEL-6406 (2.16.0, Willem Jiang, 2015): "take the Suppressed exception into
  consideration". It is a general API decision, not a failover decision.
- Since CAMEL-25114 (9ca2736acd4d, Claus Ibsen, 2026-09-28, first released in 4.23.0), `FinallyProcessor.java:140`
  keeps the doTry exception and adds the doFinally exception as suppressed (doTry-eip.adoc 227-229). Before that, the
  doFinally exception was dropped. So a cleanup failure of a monitored type now makes the load balancer fail over,
  although the failure itself (IOException) is not monitored. The next output succeeds and the IOException is lost.
- onException (`DefaultExceptionPolicyStrategy.java:74/250`) and doCatch (`CatchProcessor.java:230`) walk only the
  cause chain (`createExceptionIterable`), so failover is the odd one out (doTry-eip.adoc 211-213 documents the
  causes-only rule for doCatch).

**Evidence:**

| case | main / 4.23.0 | 4.22.1 |
|---|---|---|
| failover(IAE), attempt throws IOException, doFinally throws IAE (inline or via direct) | exception=null, second output ran, route continued | IOException, no failover |
| onException(IAE) on the same IOException + suppressed IAE | not matched (IOException) | not matched |
| failover(IAE), processor throws IOException with `addSuppressed(IAE)` (no doTry) | fails over | fails over (old CAMEL-6406 behaviour) |

**Docs:** failoverLoadBalancer-eip.adoc 225-228 ("only apply for a specific set of exceptions") and 78-80 ("If all
failed, then Camel will throw the caused exception"). Neither says suppressed exceptions count.

**Severity reasoning:** the routing is wrong and an exception is silently dropped, but only when a doFinally inside a
failover branch itself throws a monitored type. That is not common, so this is Minor. It is not intended. CAMEL-6406
chose the getException API semantics, and CAMEL-25114 did not consider the failover interaction, so no HOLD.

**Reproducer:** `logs-rtcs-a/tests/FailoverSuppressedExceptionTest.java`. On origin/main,
`testNoFailoverOnSuppressedException` fails ("expected: <java.io.IOException> but was: <null>"). The control
`testOnExceptionDoesNotMatchSuppressedException` passes. Original probes: `harness/probes/FailoverFinallyProbe.java`
and `SuppressedMatchProbe.java`. Extra probe: `logs-rtcs-a/probes/Fo2.java`.

**Fix idea:** in `shouldFailOver`, match the monitored classes against the exception and its causes only
(`ObjectHelper.createExceptionIterable(exchange.getException())`, as onException and doCatch do), not
`exchange.getException(Class)`. Caveat for the JIRA: this also stops failover in the pre-4.23 case where a component
adds a suppressed exception (row 3). That should be mentioned in the upgrade guide, or the fix could be limited to
skipping suppressed exceptions. Maintainers may prefer to keep suppressed matching and document it instead.

**Duplicates checked (none):** JIRA text (failover | FailOverLoadBalancer) x (suppressed | getSuppressed): only
CAMEL-11497 (doc migration). suppressed x (getException | doFinally): CAMEL-25114, CAMEL-6406, CAMEL-9741, CAMEL-24476,
none of them this. Summary failover x (exception | cause): CAMEL-9214 (circuit breaker, Won't Fix). gh PR search
"failover suppressed", "FailOverLoadBalancer suppressed", "getSuppressed failover": no hits.

**Affected versions:** the doFinally trigger affects 4.23.0 and main only. camel-4.22.x has no `addSuppressed` in
FinallyProcessor (4.22.1 verified), and 4.18.x and 4.14.x predate it. The underlying matching of suppressed exceptions
(same `FailOverLoadBalancer.java:135` on all branches) is in every version since 2.16, but there it needs a component
or processor that adds suppressed exceptions itself.

## 3. An exception escaping a doTry is handled by the route error handler only when the doTry is nested in another EIP

**Verdict: DOC** (the behaviour is long-standing and follows from how error handlers are applied; the new doc
sentence overgeneralises)

**JIRA summary:** doTry docs - an exception not caught by a doCatch is handled by the route error handler
(onException, redelivery of the whole enclosing EIP, dead letter channel) when the doTry is inside another EIP such as
filter, choice or pipeline

**Root cause (mechanism):** `ProcessorDefinitionHelper.java:433-443` (`shouldWrapInErrorHandler`) never wraps a
doTry/doCatch/doFinally node, or anything under one, in the error handler. The enclosing filter/choice/pipeline node
falls into the `else` branch (`:466-468`), so its channel is wrapped (`ProcessorReifier.java:713-716`). An exception
that leaves the nested doTry is therefore processed by the filter's error handler. The handler matches onException and
redelivers the whole filter, which re-runs the doTry steps and the doFinally. At the top of the route there is no
enclosing wrapped node, so the exception just fails the exchange.

**Evidence** (`logs-rtcs-a/probes/Dt.java`; onException(ISE).handled(true).maximumRedeliveries(2); identical on main,
4.23.0 and 4.22.1):

| doTry ... doFinally, body throws ISE | result |
|---|---|
| top level | exc=ISE, 1 attempt (as documented) |
| inside filter / choice / pipeline | handled by onException, **3 attempts** (doTry body and doFinally re-run) |
| inside split | the split's per-item error handler handles it, 3 attempts |
| doTry/doCatch(IOException) top level vs inside filter | ISE vs handled, 3 attempts |

**Why DOC, not a code bug:**
- The behaviour is unchanged since at least 4.14 (identical `shouldWrapInErrorHandler` on 4.14.x, 4.18.x and 4.22.x)
  and goes back to the CAMEL-1560 decision (2.0, Claus Ibsen): doTry "mimics how the Java try .. catch will behave". An
  uncaught exception propagates to the enclosing scope, and here the enclosing EIP has the error handler.
- The tests pin only the top-level case: `TryCatchFinallyOnExceptionIssueTest` and `ValidationFinallyBlockNoCatchTest`
  ("regular error handler is disabled for try .. catch .. finally"). Nothing pins the nested case either way.
- Changing the code would break a decade of routes such as choice -> doTry with route-level onException, which rely on
  this.
- The contradicting text is new: doTry-eip.adoc 221-225 ("not handled by the route error handler: onException,
  redelivery and the dead letter channel are not in use ... The exception is thrown from the doTry, and the exchange
  fails"), written in 9ca2736acd4d (CAMEL-25114, first in 4.23.0). It describes the top-level case only. It is a doc
  issue against that section.
- Point the JIRA at the surprising part: with redelivery, the whole enclosing EIP is re-run, including the doTry body
  and the doFinally. Maintainers may decide to treat that as a code issue instead. Not HOLD: no maintainer chose the
  nested semantics explicitly. It is an emergent design consequence, and the doc author did not cover it.

**Reproducer:** `logs-rtcs-a/tests/DoTryNestedUncaughtExceptionErrorHandlerTest.java`. On origin/main, `testTopLevel`
passes and `testNestedInFilter` fails ("expected: <java.lang.IllegalStateException> but was: <null>").
Original probe: `harness/probes/EhProbe.java`. That probe covers onException-block behaviour; `probes/Dt.java` is the
one for this finding.

**Doc fix sketch (2-3 lines in doTry-eip.adoc after line 225):** "When the `doTry` is inside another EIP (such as
`filter`, `choice` or `pipeline`), the exception is thrown from the `doTry` into that EIP, and the route error handler
of that EIP handles it: `onException` applies, and a redelivery runs the whole EIP again, including the `doTry` and
`doFinally` blocks."

**Duplicates checked (none):** JIRA summaries (doTry | try catch | doCatch | doFinally) x (onException | error handler |
redelivery | dead letter): CAMEL-1560, CAMEL-2577 (doTry wrapping a filter: the inner error handler disabled; the
opposite nesting), CAMEL-5201, CAMEL-7275, CAMEL-13640 (Not A Problem, split + subroute), CAMEL-21079 (Abandoned). (doTry
| doCatch) x (choice | filter | split | nested): CAMEL-7958, CAMEL-23408, CAMEL-2577, CAMEL-13640. None reports this.
gh PR search "doTry onException filter", "doTry nested error handler", "doTry uncaught onException": only unrelated PRs
(#27020 = CAMEL-25114 itself).

**Affected versions:** the behaviour is the same in main, 4.23.0 and 4.22.1 (verified) and in 4.18.x and 4.14.x (same
code). The contradicting doc text exists only in main and 4.23.0 docs, because it was added in 9ca2736acd4d; 4.22.x,
4.18.x and 4.14.x do not have it. So the doc fix targets main (and the 4.23 docs).
